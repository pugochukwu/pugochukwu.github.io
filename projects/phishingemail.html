Phishing Email Investigation

Home SOC Lab Pack · Lab 2, built on the Home SOC foundation

Solo build · TheHive · Cortex · CyberChef · VirusTotal · Wazuh-Slack alerting

The scenario

Solara Health Partners is a regional outpatient clinic network that handles patient scheduling and billing data under HIPAA. A billing employee receives an email that appears to come from the organisation's EHR vendor, asking them to "verify" a login through an attached HTML file. The employee does not open the attachment and forwards the message to IT, which is the correct behaviour. Even so, Solara's regulatory posture requires a formal, documented investigation of any suspected compromise of systems adjacent to patient data, whether or not the attachment was executed.

The work follows what an on-call SOC analyst does with a forwarded report: analyse the email headers, decode the attachment safely, check reputation, open a tracked case, enrich every observable, scope who else received the message, and close with a verdict and remediation. The email, the attachment, and the mailbox search used here were constructed for the lab, so the scenario is simulated end to end. The tooling, the troubleshooting, and the investigation process are real.

Network architecture

The lab reuses the Home SOC foundation. HOM-PC-L002 becomes the investigation platform running a new Docker Compose stack, HOM-PC-L003 keeps running the Wazuh Manager, and HOM-PC-W001 is powered off so its CPU and memory can be lent to HOM-PC-L002 for the duration of the lab. Cortex reaches the VirusTotal reputation API over outbound HTTPS.

Technology stack

  • TheHive: case management. It holds the observables, tags, tasks, notes, and timeline so the investigation has structure and a reviewable record
  • Cortex: the analysis engine connected to TheHive. It runs analyzers against case observables and returns the results inside the case, so enrichment is consistent and recorded
  • VirusTotal: reputation intelligence for domains, URLs, IP addresses, and file hashes, used manually and through Cortex with an API key
  • CyberChef: the decoding workbench for attachment triage, used to peel back Base64 and JavaScript encoding without opening the file in a browser
  • Wazuh and Slack: a level 12 alert integration so high-severity telemetry from all four agents reaches an analyst channel in real time

Resource reallocation

TheHive, Cortex, Elasticsearch, and Cassandra cannot run reliably on the baseline VM allocation. HOM-PC-W001 was shut down cleanly with its configuration left intact, and HOM-PC-L002 was upgraded to 8GB RAM, 4 vCPU, and a 60GB disk. The allocations are to be reverted once the lab is complete. Zeek on HOM-PC-L002 was stopped, not uninstalled, to free more CPU and memory.

Wazuh-Slack alerting

A Slack integration was added to ossec.conf on the Wazuh Manager with a level 12 threshold, applying to all four agents. It was verified in three steps: the integration daemon confirmed the integration enabled after a manager restart, a direct test message was posted from the manager terminal, and a custom level 12 alert payload was passed through the integration script to prove the formatted alert path.

Building the investigation platform

Docker Engine and the Compose plugin were installed from the official repository, and the StrangeBee Docker repository was cloned with the testing profile selected, because it provisions TheHive and Cortex together on one server and fits the 8GB, 4 vCPU host. The profile pins Cassandra 4.1.12, Elasticsearch 8.19.22, TheHive 5.8.0, Cortex 4.1.0, and Nginx 1.31.6. The first startup did not go cleanly, which is covered below because it is part of the work.

Cortex analyzers and the permissions bug

VirusTotal GetReport, URLhaus, and DomainMailSPFDMARC were enabled in Cortex, each with a TLP:AMBER and PAP:AMBER sharing policy. The integration was tested from TheHive against the EICAR hash and 8.8.8.8. The first four analyzer jobs failed with only a job folder path as the error. Cortex runs as UID 1001, while the host folders it writes to were owned by root and by the lab user, so it could not write job output. Ownership of both folders was changed to 1001:1001, Cortex was restarted, and the same jobs then succeeded.

Network connectivity and tuning

New TCP connections from the analyst workstation to HOM-PC-L002 began timing out while ping kept working. Diagnostics on the host showed TheHive, Cortex, and Nginx healthy, the right IP bound, and no firewall or connection-tracking limit in play. A packet capture showed HOM-PC-L002 answering every attempt, which placed the fault on the return path to the workstation. The workstation's Wi-Fi profile was corrected to Private and a stale ARP entry was cleared, after which connectivity returned. Nothing on HOM-PC-L002 itself was changed. Separately, Cassandra's health check interval was relaxed to cut a constant CPU load.

CyberChef deployment

CyberChef was deployed as a standalone container, independent of the TheHive and Cortex stack. It was first published with a port mapping that did not match the image's internal Nginx port, so the service was unreachable even though the container reported healthy. Recreating it with the corrected mapping fixed access.

Building the simulated phishing sample

With the platform ready, the sample was built on HOM-PC-L002. The HTML attachment holds a Base64-encoded JavaScript redirect to a fictional, non-resolvable domain. The email was assembled with mpack so the attachment is a real MIME part, then spoofed headers were inserted: a Return-Path, a two-hop Received chain, failing SPF, DKIM, and DMARC results, and a From address impersonating a fictional vendor, MedLink Health. A mailbox search result listing five Solara staff recipients was also fabricated for the scoping step.

Email header analysis

The headers show several indicators of sender spoofing. The originating server identified itself as mail.medlink-health-portal.com in the HELO, while the receiving server logged it as unknown. The originating IP, 198.51.100.44, sits in the TEST-NET-2 documentation range (RFC 5737), which is not used for live mail delivery. The Return-Path points to a domain styled to resemble Solara's EHR vendor. The second Received hop shows normal internal delivery once the message entered Solara's mail environment.

Attachment triage in CyberChef

The attachment was examined without opening it in a browser. A Base64-encoded JavaScript block wrapped in an eval(atob(...)) construct was located in the file. The From Base64 operation in CyberChef decoded it to a redirect to https://secure-medlink-verify.net/login?session=redirect, a domain distinct from the sender's domain. The SHA-256 of the attachment was then extracted from the command line.

Reputation checks in VirusTotal

Both domains returned a detection score of 0 out of 93 alongside an Error() status and unresolved fields, meaning the scanners could not reach them rather than confirming them as safe. The attachment hash returned no existing report, meaning it had never been submitted before. A clean score on a brand-new phishing domain is inconclusive, not exculpatory, so the verdict does not rest on reputation alone.

TheHive case

A case was opened as High severity with TLP:AMBER and PAP:AMBER. A task checklist covers header analysis, attachment triage, reputation checks, Cortex enrichment, scope assessment, and the closing report. Five observables were added as indicators of compromise: the spoofed sender domain, the redirect domain, the originating IP, the attachment's SHA-256, and the spoofed sender address.

Observable enrichment through Cortex

Analyzers were run individually against all five observables from inside TheHive, and the results were registered against each artifact. Eleven jobs ran in total. Nine completed, confirming no VirusTotal detections, no SPF or DMARC records for the sender domain, no CIRCL or URLhaus matches, and a non-routable originating IP. Two failed. The Abuse_Finder analyzer returned an NXDOMAIN error querying the sender domain's MX record, which confirms the domain has no DNS presence. The Inoitsu analyzer failed on a regular expression error inside the analyzer, a tooling issue unrelated to the observable.

Verdict and closing report

Verdict: malicious. The reported email is a credential-harvesting phishing attempt impersonating Solara's EHR vendor. Four independent lines of evidence support the verdict:

  • Header analysis found a hostname mismatch, an originating IP in a non-routable documentation range, and failures across SPF, DKIM, and DMARC
  • Attachment triage found a deliberately obfuscated JavaScript redirect, hidden behind Base64 and eval, pointing to a separate unaffiliated domain styled as a login page
  • Enrichment found no legitimate infrastructure behind either domain, and Abuse_Finder confirmed through DNS failure that the sender domain does not exist
  • No single check carried the verdict. The absence of VirusTotal detections for a brand-new domain was treated as inconclusive, so the conclusion rests on header and content analysis

Recommended remediation:

  • Block the sender domain and address (medlink-health-portal.com and support@medlink-health-portal.com) on the email security gateway
  • Block the redirect domain (secure-medlink-verify.net) in DNS or web filtering, including for personal devices outside corporate email filtering
  • Force a password reset for s.patel as a precaution, whether or not credential submission can be confirmed
  • Issue an awareness notice to all staff describing this campaign: vendor impersonation, an urgency-based subject line, and an HTML attachment requesting login verification
  • No further action for the other recipients beyond the awareness notice

The case is recommended for closure as Resolved once the remediation is complete. The documented investigation also meets Solara's requirement to formally review any suspected compromise adjacent to patient scheduling and billing data, whether or not a compromise occurred.
